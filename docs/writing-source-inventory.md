# Declared source inputs and kernel standing

A source-owner inventory is a bounded observation of one declared subsystem. It
uses the existing system description, Source-contract providers and repository
readers. It creates no semantic node, acceptance, permission or published state.

Select the exact subsystem reference and follow its issued source-inventory read.
The read returns declared modules, public inputs, explanation and evaluator source
with full raw-source pins. Evaluator code is labelled as source, not a passing
check. The Source kernel's contract chooser issues `projection='inputs'`, carrying
its actual project lens where applicable. This closed optional selector returns
the same subsystem reference, scope, cut, raw-pinned file rows, roles and exact
read handles. It does not assemble contract or capability metadata. Those lists
are empty and coverage explicitly marks `contract_relations` and `capabilities`
as `NOT_REQUESTED`, not absent or verified. No source body fanout, cache, index or
new endpoint is introduced.

The inventory ceiling remains 15360 bytes. Requested page counts are upper bounds.
Follow the issued advancing continuation, retaining its projection, project lens
and cut. If even one row cannot fit, the existing budget refusal remains. Changed
inputs refuse a stale cut. Exclusions, privacy and unavailable states are unchanged.
HTTP, native and SDK requests share the owner-discovery grammar, with the selector's
closed schema delegated to `source_inventory.contract`. The SDK follows the issued
descriptor without a separate input grammar.

The Python convenience wrapper also accepts the existing optional selector:
`sdk.source_inventory(reference, projection='inputs', root=workspace)`. Omitting
it keeps the same rich metadata default; it does not raise the response ceiling.

Omitting `projection` preserves the rich legacy metadata route through existing
owner reads. Registered Source contracts retain their separate declaration versions,
segment bases and typed relation counts. Follow each issued segment request to
read its exact typed consumers through the existing Source-contract owner. Bind
the offered selector through the template's `field` (SDK request) or `query_field`
(HTTP query), using only its supplied values; the
coarse contract read also has native and HTTP handles. Compare returned current
versions/bases with the inventory observation: an unretained historical version
is never invented. Capability operation bodies likewise stay behind their exact
inspect requests. Coverage identifies these summaries; no schema or relation
body is silently truncated. These facts are not review acceptance.
A different declaring-source edition is explicit unavailable rather than replaced
by the executing library's version. Runtime declaration values and current disk
source pins are separate observations. Equal disk bytes do not establish which
Python code was loaded before a same-path edit; `runtime_source_linkage` therefore
remains `UNVERIFIED_LOADED_CODE`. It is not an executable-source attestation.

Existing repository reads carry each exact source pin. A human Material reading is
offered only when an actual permitted project context exists; an unavailable or
ambiguous repository has no invented alias. Page with the issued cut. Changed
source refuses the old observation; current reinspection is explicit. Raw source
bytes are not rewritten or included in the inventory response.

The kernel field is `UNRESOLVED` when no explicit ingested counterpart is declared.
An architectural label such as `domain.work` is not a memory-node identity. This
read performs no fuzzy matching, semantic-store scan or global absence census.
The inventory and its basis can be named as inputs to an authored checkpoint;
actual ingestion, publication and independent reconstruction require their own
existing owner receipts. A file merely indexed as text or drawn in a graph is not
proof of usable typed self-ingestion or a completed self-modification loop.

The existing Backlog now offers a read-only **Source inspector**. Select a declared
contract, then an actual retained `kernel.declared-source` Work publication. Its
prepared meaning, current owner standing and explicitly verified fold counterpart
remain separate. The inventory's `UNRESOLVED` field performs no automatic identity
lookup. Follow issued selected reads; see [the bounded Source-kernel bridge](source-kernel-bridge.md).

Only bounded declared code/configuration and exact public declaration inputs are
inspected. Broad knowledge, docs and profile trees are not expanded, and private
state, author history, personal canon and host reader proof remain excluded.
Coverage names unavailable inputs instead of claiming a complete whole-system
model. Source grants, manuscript Apply and ordinary workflow limits stay separate.

## Distribution selection

`scripts/writing_eval_manifest.py` owns `OPERATIONAL_INPUTS` and its deterministic
container projection. The exporter consumes that same declaration. Both ordinary
and refresh `.dockerignore` files are generated; adding an operational guide or
exporter Python tool no longer needs another manually maintained allowlist entry.
Existing image source/resource classes, portable evaluator subset and private
exclusions remain separate from project-data selection.

From the source checkout, explicitly generate or check the two selectors:

```sh
python scripts/writing_eval_manifest.py --repo-root . --write-docker-selectors
python scripts/writing_eval_manifest.py --repo-root . --check-docker-selectors
```

The check reads only those maintained declarations and selectors. It does not
export data, build an image, run providers or certify scientific/privacy acceptance.
Published source/image/closure manifests remain the authority for shipped bytes.

## Source and data cutoffs

An updated application source inventory does not update the mounted workspace's
Work records or preferred order. A distribution can carry new source against its
explicit frozen 22-project/65-session/3-PDF data snapshot. Its entry and acceptance
record must name those cutoffs separately; recipient backlog counts and plans
are observations of the recipient data, not copies of the live author backlog.

A checkpoint that needs engineering programme facts must name the exact existing
Work/plan observation and its consumed basis separately from this code inventory.
Use the existing Work reads and explicitly selected project/object handover where
its closure admits those records. Carry only permitted source/metadata and
recipient-resolvable references. This read exports no Work ledger, author history
or private document, creates no parallel plan, and grants no sharing consent.

The registered operation providers also include
`domain.representation:source_publication`, authored by the existing publication
owner. Its current declared parts and primitive steps are selective Source reads,
not a new executor or an architectural-label-to-memory-node mapping. Current disk
pins remain `UNVERIFIED_LOADED_CODE`. Exact Work-retained versions, current review
standing and actual active kernel counterparts keep their separate owner reads.
See [Selected Source meaning and kernel recovery](source-kernel-bridge.md).

## Reading a declared input in the workspace

Inside the app, the owned workspace HTTP door also issues one body read for each
inventory row, as `read.workspace_read`. It is a `source-input` request naming the
subsystem reference, the inventory cut (`as_of`), the row path and its whole-file
pin, with a character `offset` and `limit` of at most 16,000 characters. Before any
byte is read the inventory owner proves the selection again: the cut must still
hold, the path must be a declared input of that owner and the file must still match
its pin. The configured repository target is derived from the row, so no
caller-supplied project, alias or path grants access. Native, SDK and project
callers are refused before the body and keep using the row's repository read. The
page carries no filesystem path. Its next and previous reads keep the same cut and
pin, a moved file or cut refuses, and its restart read returns to the current
inventory. A page that would exceed the 15360-byte ceiling is returned as a smaller
exact page of the same bytes.

A role selection such as `role='explanation-source'` pages inside the same cut.
The System owners view uses it to offer an owner's declared explanation before its
implementation files, then follows each row's body read in the same visit, so Back
returns to the inventory page and control that opened it.

The promoted writing-artifact reader states its painted extent above the body:
`Complete · m characters · read at …`, or `Partial · characters a–b of m` for the
scalar range this page actually covers (file bytes stay in the status line). Its
Continue control names the next requested range; one continuation is in flight at a
time, at the reader's exact pin, and a stale or changed page never repaints. Back or
Close returns to the exact opener that issued the read, never to a guessed page.
In a Work view, Now names the acting app turn or external actor, when it was
observed, and the one turn a Stop would touch; opening that conversation confirms
the current turn before Stop is offered and never retargets a newer turn. Next leads
with the owner-issued next step when the owner issued one, and otherwise says that
none is issued at this read. Below it the owner's permitted actions are listed by
kind: a form here, an owner-issued template shown as issued and not sent from here,
or an inspect-only read, plus the existing Progress and next action part. A permitted
form is available; it is not promoted or recommended by its place in the list. A
pending inline read can be
cancelled; Cancel ends only that read and returns focus to its opener. These labels
describe the current owner response; they are not acceptance or permission.

Reading a page is orientation. It is not execution, review, publication or a claim
about loaded runtime code. Markdown is rendered inertly, and only once the complete
text of one cut has been joined from these continuations. Raw stays the exact text.
