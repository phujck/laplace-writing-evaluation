# A configurable workspace for work, writing and agents

Ownership/placement correction for Root synthesis · 21 October 2026 · no prototype, production implementation or physical migration authorised

A person should be able to build a workflow, understand what it will do, start it within chosen limits, and intervene at the part that needs attention. Opening a paragraph, role, simulation or campaign should reveal its purpose, present state, relationships, available actions and the consequences of those actions. Changing presentation must not change the system’s rules.

This design covers the full interaction architecture. The completed source/path refactor is its starting system. It proposes new frontend organisation and identifies the backend contracts still needed for the requested experience. The parked company roadmap and closed science campaigns are not restarted.

The working evidence is in [the capability inventory](../corpus_friction/development/frontend-design-20261021/capability-inventory.json), [settings inventory](../corpus_friction/development/frontend-design-20261021/configuration-inventory.json), [currentness calibration](../corpus_friction/development/frontend-design-20261021/explanation-currentness-calibration.json), [module observation](../corpus_friction/development/frontend-design-20261021/frontend-dependency-observation.json), [method research](../corpus_friction/development/frontend-design-20261021/method-research.md) and [research decision](../corpus_friction/development/frontend-design-20261021/method-decision.json). ## Ownership before containers — reopened author correction

The system, a subsystem, a contract, a document, a claim and a simulation are selectable objects at their useful grades. A campaign coordinates desired changes across such objects. Work targets their actions/results. A manuscript project is one applicable collection and operating context; it is not the mandatory parent, identity authority or permission root of every object. This corrects a missed premise in the earlier design. The physical source/runtime/current-run consolidation remains delivered; general logical campaign/Work/evidence ownership and its API/admission/navigation migration remain open.

### Five separate decisions

| Concern | Design rule | What does not decide it |
|---|---|---|
| Stable identity | Each object has an owner-issued persistent object id and explicit version references, independent of its title, project membership or path. Existing ids are retained as exact legacy aliases; the responsible owner, not a renderer, issues a future binding | Moving a file or changing a display label does not create a different object |
| Logical responsibility | One authoritative owner decides each facet/action/invariant. A system composes subsystem and contract owners; document/source/claim/review facets can have distinct responsibilities. An owner binding has its own version | A directory, campaign, project or human coordinator is not automatically the decision owner of everything it contains or mentions |
| Authority and action scope | The admitted actor, actual role/mode/grant, target, consumed constraints and exact effect determine permission. A selected scope is an action/read boundary, not a grant | Membership in a cross-scope campaign or navigating into another project never grants its writes |
| Grouping and navigation | Campaigns, collections, projects and views organise relevant references. Containment, target, dependency, review, custody and coordination are distinct relations. The same object can participate in several campaigns without duplicated Work/history | A navigation tree cannot manufacture ownership or an execution prerequisite |
| Physical custody | A custody reference says who retains which exact bytes, where, under what access policy, and through which artifact/body/repository reader. Byte identity, producing act and engineering/scientific acceptance are separate | A shared ledger or deep evidence directory is not proof of general logical ownership or evidence authority |

A general reference therefore carries a stable object identity and requested version, its responsible owner binding, applicable read/action scope, and declared legacy/custody handles where needed. Owner binding, semantic version and byte/custody version are different facts. A later authorised owner transfer can preserve object identity while recording a new responsibility binding. It cannot silently widen an old grant or renew an old review. New ids/bindings are not allocated by this design and no current namespace is renamed.

For existing Work, the current `(project namespace, local Work id)` remains the exact legacy identity until its owner admits an additive binding. Do not assume local ids are globally unique. The compatibility mapping is one-to-one for that qualified pair, preserves collisions explicitly, and gives the same object a general reference rather than cloning it. Preserve an existing native id as the identity payload; an added owner-qualified binding must not mint a competing object/history for it. New objects obtain identity only from their actual creating owner. The proposed general metadata belongs in the existing owning Work/artifact/relationship records and their derived indices; there is no new parallel object/alias/evidence registry to maintain by hand. Source-defined contracts obtain their identity/owner declarations from their actual contract owner; persisted Work, documents and results obtain bindings from their canonical record owners. The structural system description may present these references, but it is not a substitute permission or acceptance owner.

### Campaigns coordinate; Work targets; owners decide

A campaign has a purpose, coordination/relevance edges, bounded integration criteria and participating object/Work references. It does not acquire ownership of their source or permission to operate them. Work states its desired result and its qualified target object(s)/actions, consumed constraints and responsible executor/reviewer. Existing containment can organise delivery, while an explicit consumed dependency determines propagated acceptance. The current `parent_work_id`/`depends_on` validators are project-local; cross-scope coordination must not be encoded by inserting a foreign id into those fields.

The general relationship surface distinguishes `coordinates`, `targets`, `owns-facet`, `contains`, `consumes`, `requires`, `reviews`, `explains`, `produced-by` and `custodied-at`. Their domain owners supply meanings and legal operations. In particular, `coordinates` does not imply `requires`, and `explains` does not make a document the owner of the described code. A subsystem or contract can be the selected working root with no manuscript project. A project-specific view is offered when a document/collection is actually relevant.

There is no reserved “system project” workaround and no blank-project bypass. A general owner/scope contract must be explicitly added to existing identity/admission owners; until then the old routes still require their real project namespace. A new resolver can discover the old reference, but only the original or explicitly extended authority contract can admit its effect.

The current shared `corpus_friction/work_orders.jsonl` already provides one canonical Work history. Its folds, APIs, identities, admission and navigation still select project namespaces; `logical_target` is not a completed general cross-scope target/admission model. The needed extension is owner-qualified target/responsibility/reference semantics in these existing owners and adapters, not another ledger or a renamed folder.

### General settings and reusable definitions

Select the actual governing scope path for the assigned action: system policy, responsible subsystem/contract or domain qualifications, reusable workflow/step/role assignment, target object/task, and an applicable project/document context **only when that key actually consumes it**. An arbitrary collection/campaign path is not an instruction inheritance chain, and multiple memberships are not merged. Each key still declares its legal scopes, precedence/composition, winning meaning, relevant absence/binding/ceiling facts, display provenance and edit guard. A system-default change overridden by a subsystem remains shadowed exactly as in the A/B trace; unrelated document context does not become an input of a backend operation.

Retain current local rules: author conversation preferences apply through their actual project/session owner; dispatched worker/judge model selection still does not inherit the author's project preference; architecture preferences are currently workspace-only; active session settings remain next-turn-only. General system/subsystem/contract policy writes are missing semantics, not UI permission toggles. Owner/scope discovery may expose those values and limits before any new mutation is admitted.

A reusable workflow definition has an owner-issued stable definition id, immutable version and stable step/assignment ids; it is logically owned by the relevant system/subsystem/domain workflow owner. Editing creates a version; a deliberate fork creates a new identity with a `derived-from` relation. The earlier `(project, artifact path)` is only a legacy custody/resolution alias. It is not the universal definition identity. Shipped `profiles/workflows` templates remain source resources of the workflow owner; existing document-specific definitions keep their artifact/version history. A new system-owned definition must not require inventing a manuscript project to save it. Extend existing bounded artifact/body custody with explicit owner scope and storage bindings, while the workflow owner validates its typed edits/compilation. No second configuration store is created.

### Evidence responsibility and custody

Evidence is qualified by the object/version, action/effect, claim or review it supports; its producing owner/act, responsible assessing owner and allowed scope; and its exact artifact/body/repository reference. The producer, custodian, subject owner and independent reviewer are explicit roles. A hash proves bytes, not permission, relevance or acceptance. A campaign can link an evidence record without owning its subject, disclosing private bytes, or accepting its claims.

Keep the existing body/artifact/journal stores and review/receipt owners. Add subject/responsibility/custody relationships in their canonical metadata, and derive the evidence explorer from those records. It must show current support, historical support, unavailable material and pending assessment without manufacturing a global green state. Public cross-scope metadata and private body access are separate permissions; restricted titles/contents are not fetched merely to draw the graph.

Current development coordination remains at `corpus_friction/development/current.json`, owned by system development/operations. This design and its working records already live in system documentation and that development home, not a manuscript bucket. Future active grants, handoffs and results belong to their actual Work/grant/review/delivery owners: retain the canonical phase/authority record, exact payload/body and its current owner read. They are discovered through **System → subsystem/contract → campaign → selected Work → authority/results/evidence**. An explanatory grant JSON is not a second capability authority. New materialisation uses an explicitly admitted custody binding under the current owning subsystem; it is not a reason to copy old ledgers or create another project.

Historical `evidence/WRITING_JOINS_2026-10-04/codex-continuation` grants/returns/proofs stay at their immutable coordinates and hashes. Their subject/owner/custodian links and stable legacy read handles provide discoverability. Existing manuscript originals, saved versions, artifact records and private body references also stay. The default design decision is **no bulk byte relocation**: change logical bindings/current entry views only when implemented and authorised. A future physical move needs its own reached consumer/identity/authority/rollback witness; no move is authorised now.

## 1. The experience and the method

**Proposed decision for Root review: use React for the new shared workspace interaction surfaces, with React Flow behind a workflow-canvas adapter.** Use one interaction/service spine and retain the current exact-source editor, issued-basis draft machinery, qualified owner reads, observer semantics and bridge fence. Do not introduce Lit as a third default presentation system. Existing native views remain a migration boundary until each replacement is accepted; the target is not a permanent collection of native, Lit and React versions of each control.

The method research’s native-module recommendation is a useful baseline, not an approved architecture. Its conditional case for a workflow editor is reached: direct assembly, nesting and role-topology editing are central author requirements. We therefore choose the graph-oriented method for the proposed new experience, while keeping backend and interaction contracts independent of it. This is a design decision, subject to Root review and bounded feasibility authorisation before any prototype or production work.

| Approach | Fit to the required experience | Main cost and reason for this proposal |
|---|---|---|
| Restructure native ES modules and extend the existing SVG/list graph | Retains current deployment and allows complete renderer control | Drag handles, ports, connections, nesting, keyboard editing, selection and interaction lifetimes need substantial bespoke work. Existing graph is a typed display, not a workflow editor. A viable alternative, but migration convenience alone does not settle the required experience. |
| Native services with Lit components | Explicit component lifecycle and incremental reusable controls | Does not supply graph-editing interactions. Combining it with a React graph introduces two component systems; building a separate graph editor retains the larger custom-interaction cost. Not the default. |
| React workspace renderer with an isolated React Flow canvas | Component composition and a mature direct-manipulation graph surface suit the central workflow/role editor | Adds an explicit build/offline dependency and served-asset route that does not currently exist at repository root. Must preserve the current owner/draft semantics and test migration, bundle size and low-end behaviour. React Flow grouping is presentation; it does not implement nesting authority or workflow execution. |

Official [React Flow accessibility guidance](https://reactflow.dev/learn/advanced-use/accessibility) documents focus/selection/movement and ARIA mechanisms; application-level accessible actions still need to be designed. Its [subflow documentation](https://reactflow.dev/learn/layouting/sub-flows) makes grouping a positioning mechanism, so our owner decides semantic nesting. [React external-store subscriptions](https://react.dev/reference/react/useSyncExternalStore) offer a way to subscribe to retained non-React services without moving draft authority into component state. These support the proposed separation; they do not prove this migration works.

These are source-based assessments, not measured performance results. The primary-source comparison and licence details are retained in the method research. React Flow’s graph/list equivalence and our domain actions still need design and task evidence. We retain the existing CodeMirror adapter and textarea fallback; an editor-library replacement has no reached purpose.

The cohesive reason for using React beyond the graph is the shared operator surface: object headers, role editing, effective settings, command/result panels, situated conversation and return navigation must compose consistently around the selected region. A common component/lifetime model can serve that experience. React Flow alone does not prove the case. The credible alternative is a restructured native shell with one isolated graph/editor region; it avoids migrating sound views, but retains more manual composition across the shared inspector/conversation/control system. Neither approach earns a measured size/performance advantage from the present evidence.

The proposed first code boundary is existing guarded Work read/action integration through the shared shell and replaceable renderers (section10). The required workflow/role definition editor follows in P3 once its own edit/compile contracts are admitted; it is not faked by storing arbitrary JSON or treated as delivered by the first boundary. Neither boundary requires migrating every document/research view. Existing views and the exact-source editor can remain opaque adapters until a real task/ownership boundary justifies replacement. This is a full interaction architecture with staged migration, not an instruction to translate all117modules into JSX.

A **fully operable outline/list presentation of the same workflow region** provides the non-dragging and narrow form. Rendering it in React alone would not prove replaceability. The required renderer-neutral port uses serialisable object references, owner read/action handles, immutable result snapshots, intents, receipt/refusal results, cursors and visit/return coordinates; it contains no React element, context, hook, proxy store or DOM node. A later bounded conformance exercise must mount a plain-DOM outline outside a React root, read the same selected region and perform/recover one admitted operation using only that port. A custom frontend must also be able to call the underlying owner contracts directly within its admitted scope; a general owner/object reference need not carry a manuscript project. This is a specified proof obligation, not a prototype/result already obtained. No Lit runtime is introduced by this proposal.

## 2. The common object and action model

Reuse qualified owner identities and revisions. A general object reference names its stable identity, responsible owner binding, version and admitted scope, with owner-issued read/action/custody handles. Existing project namespaces are explicit legacy/local qualifications, not the universal identity or owner. Its views expose common facets: purpose; standing and observed activity; relevant relationships; inputs/outputs; settings; actions; feedback; and history. A section, a Work item, a role assignment and a result specialise those facets through their own contracts. We do not force all objects into Work or mint a second set of object IDs.

A **workflow definition** is a reusable owner-qualified object independent of a manuscript project; it describes versioned steps, nested objects, role assignments, typed relationships and permitted advance/effect policy. A **run** refers to the definition/version it actually consumed and to its real Work, sessions and effects. Changing a definition does not edit a running provider’s instructions. The relational model admits cycles and recursive message/feedback networks. Hierarchical containment remains well-formed and distinct from reference, dependency, review and delivery edges. A visual group is not automatically ownership, a prerequisite, a permission boundary or a cancellation group: each relation has its declared meaning.

Existing Home/Token/Request/Affected/Receipt/Refusal, Work relationships and operation contracts provide useful constituents. They do not yet provide one complete polymorphic object-facet API, a general editable workflow-definition owner or an effective-settings cascade. Those are explicit backend joins in section 8.

An action presentation carries its authoritative owner route, required read basis/guards, permitted fields, authority explanation, affected scope, expected result, pending obligations and recovery handle. The controller obtains these from owner declarations. It does not derive write permission from a status colour, a graph edge or a cached response. Client rules such as retaining an unsaved draft are legitimate local protections and survive the refactor.

A command proceeds through a local lifecycle:

1. Select an object and obtain the actual action/basis it needs.
2. Preserve the original basis while editing. A human-invoked operation can expose its effect preview; an already authorised unattended operation proceeds under the selected owner policy without a mandatory confirmation dialog.
3. Submit that admitted command once. Keep the attempt identity through retry/recovery where the owner supports it.
4. Show the owner’s effect receipt, useful partial result or scoped unmet precondition.
5. Observe the postimage before reporting the view current. Unknown observation is shown as unknown, not running or failed.

A source conflict preserves the typed text and offers comparison. An absent derived PDF is not a reason to block a source-repair action that does not consume that PDF. Rendering and observation failures do not silently renew a basis or replay an effect. Unrelated work remains available.

## 3. Hierarchy, navigation and attention

The general entry is **System & scopes**, with subsystem/contract/object exploration, **Campaigns**, **Work**, **Evidence** and applicable domain views. A selected document/project can offer Overview, Workflows & work, Manuscript, Ideas & evidence and Material as its local presentation. A backend contract offers its own source/consumer/action views without inventing a manuscript. Activity and settings belong to the selected owner/object; system policy remains in system scope. These are views of responsible owners, not new lifecycle subsystems.

The header preserves the selected owner/scope and object/contract path, an optional project/collection qualification, and a reliable Back route. It starts from system/campaign/subsystem when that is the actual task; the presence of a document elsewhere in the campaign does not make it the parent. At the selected level show one purpose statement, meaningful state, the next useful action and a small related region. People may switch graph/list/document/table presentations without losing selection or drafts. Opening detail expands that object; it does not fetch the whole project or every descendant.

The workflow view separates **Plan** from **Run**. Plan edits a versioned definition and role topology. Run displays the definition version actually consumed, current actors and effects. Node badges distinguish configured role, queued request, observed running process, returned result and independently accepted result. A proposed or expired actor is never drawn as live merely because its node exists.

Wide screens can show a region, inspector and optional situated conversation. Narrow screens show one main surface at a time with persistent object path and explicit switches to Details or Conversation. No shrinking the graph into unreadable cards. The accessible outline offers Add, Move, Connect, Nest, Assign role and Inspect actions with the same owner commands as drag/drop.

The outline controls support ordinary click/tap as well as keyboard commands. This is deliberate: [W3C guidance on dragging movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html) distinguishes a non-dragging pointer alternative from keyboard support. We must evaluate both in later task checks.

Every region has a bounded page/window. Existing `workspace-topology` folding and boundary reads are useful; accumulating every page indefinitely is not the new default. Expanding a boundary keeps a return anchor and reports which region was added. Focus, scroll and selection belong to the visit; retained drafts belong to their draft owner across visits.

## 4. Settings, authority and running versions

Settings use one inspector, with domain-owned rules for each key. It shows: effective value, source scope, explicit local value, inherited alternatives, version, who may change it, affected objects, and when the change applies. It never implies that a read-only declaration is editable.

| Setting family | Composition and authority | Boundary during a run |
|---|---|---|
| Presentation | Local view preferences; no effect on backend authority | Apply immediately to this view; retain a usable narrow/list form |
| Instructions and purpose | Ordered, identified instruction segments from applicable system/subsystem/contract/definition/step/role/object scopes, with a project/document context only where relevant; handoff/background material remains distinguishable | A run retains the exact admitted instruction basis. Save a future version; no invisible instruction replacement inside a running provider |
| Model/provider/effort | Resolve the declared role assignment and explicit permitted overrides against the actual provider catalogue | Existing session owner changes the next turn only and refuses during active work. Stop/wait, inspect then configure; no frontend workaround |
| Budgets and advance policy | Domain owner validates cost, depth, fan-out, retries and stop conditions for this operation/run | Changing future limits does not erase completed effects. Applying a stricter stop to active work is an explicit owner control with an effect receipt |
| Authority and sharing | Effective capability is constrained by the applicable grant, role and object/source scope; instructions never enlarge it | A desired expansion is a separate authorised grant request. Revocation and partial-effect handling require explicit owner semantics |

The current architecture-preference profile is workspace-only: its owner explicitly rejects a project override. The proposed inspector must show that restriction. Legal scopes are per-key facts; drawing a project/step hierarchy does not manufacture new override rights.

Scope is not one universal “most local wins” string merge. Each setting key declares legal scopes, precedence and combination. For a role’s model choice, object/task assignment may be the final override if admitted; an instruction is a composed segment; an authority constraint intersects the ceiling. Two incomparable assignments produce an explained local conflict, not an arbitrary winner. The inspector shows the actual resolution path for the selected key.

The proposed resolver follows the governing scopes of one selected action/assignment: system defaults and responsible subsystem/contract or domain policy → reusable workflow definition and containing steps → role assignment → selected target object/task, inserting a project/document context only where that key declares it applicable. This is not a universal project-parent chain. A task with multiple memberships names the relevant assignment and governing policy; it does not merge every campaign/container ancestor. An absent local entry means inherit, while an explicit empty value is handled by that key’s contract.

For `provider`, `model` and `effort`, the most specific *permitted explicit value on that path* wins, then the actual provider/model owner validates it; it does not silently fall back after a refusal. The inspector expands every source/version and the decisive override. For instruction segments, the owner declares the applicable system/domain/definition/step/role/object order and any local document/project segment; a replacement can target only an explicitly replaceable segment at a scope the author may edit. Fixed operating law/kernel and authority constraints are outside that replacement mechanism. Handoff/background documents are shown as context, never injected as instruction by this resolver.

For authority, intersect the applicable grant and role/object/source constraints; a preference cannot lift a ceiling. For budgets, the selected requested limit is bounded by every applicable ceiling and remaining cost. For advance policy, only actual chosen human/review boundaries constrain the relevant transition; a child cannot silently bypass an ancestor’s specifically required review. A review boundary does not itself mean a human boundary. Changing that policy is an explicit setting action, with its affected scope shown. These rules resolve the governing owner/assignment/target case, with project qualification only where applicable, without pretending instructions, budgets and permissions share one merge algorithm.

The effective-setting result is identified by key, selected assignment, effective value, ordered consumed origins/versions, override permission/reason, authority ceiling and application boundary. Human settings and agent admission consume that same result. Existing owners supply parts of this; the general resolver/result is a specified construction requirement, not a claim that it is already served.

Autonomy separates **advancing work** from **applying effects**. A step may automatically pass a proposal to reviewers while source application waits for an accepted review. A subsequent accepted result may automatically apply within its source grant and budget, while public publication waits for a human if that boundary was chosen. There is no universal Ask/Send/Approve step after each return.

The policy declares conditions for advance, source application, recipient routing and external/public effects separately, plus owner-configured cost/time/iteration/depth/fan-out limits and recovery behaviour. It may run an unattended review/revision loop: writer produces v5 → independent reader returns a consequential gap → writer produces v6 → reviewer checks the changed scope → accepted v6 applies through the guarded source owner → next stage advances. The loop stops on its actual acceptance criterion, a real authority/precondition failure, its configured budget, cancellation, or an unresolved material decision whose policy requires a human. Useful proposals, judgements and committed effects remain available at every stop.

No production numeric defaults are selected in this design. Owners may offer documented presets whose values are justified from task risk, observed cost and recovery behaviour, and the author can inspect/change their permitted limits. The example dashboard shows one explicitly configured finite run, not an invented engine-wide default. A stopped-at-limit run is not automatically a request for human review; its owner exposes the permitted continuation or future scheduled policy, with the retained basis and remaining obligation.

Every running step displays the definition/configuration version it consumed. A definition edit can be saved for future runs independently. Applying it to active work requires the actual supported boundary: after the present effect, stop-before-next, or an explicit replan retaining previous effects. Existing next-turn model settings remain constrained by their current owner. Cancellation stops future effects where supported and preserves committed ones; it does not roll them back or cancel unrelated work.

## 5. Comments and bounded feedback

A paragraph comment remains one originating comment with its exact source/selection basis, author and content. Response feedback keeps its existing response identity rather than pretending to be a paragraph. Routed work refers to that origin; it does not create rewritten copies of the author’s comment.

For a comment such as “Does this conclusion still follow if the boundary changes?”, the owner resolves explicit relations to the selected section’s Work, reader/argument plan, supporting evidence or simulation, and reviewers. The routing panel states each recipient and why it is relevant, its inputs/authority and unaffected neighbours. Under an authorised automatic routing policy, saving the comment starts those deliveries without another Send confirmation. The person may inspect or intervene locally; a manual policy can instead require a preview/choice. The owner asks only when the selected policy, a material unresolved decision or an actual authority expansion requires it.

Each delivery is keyed by origin, recipient, route generation and consumed basis. It has separate prepared, delivered, acknowledged, returned and accepted/rejected observations, with attempts and errors inspectable. The acknowledgement means the recipient received the scoped request; it is not evidence that the claim was repaired. Existing Work delivery supplies durable identity/continuation/recovery constituents; general multi-recipient relevance and routing still need owner semantics.

Fan-out, depth, retries, elapsed cost and repeated review are bounded by the selected owner policy. They have no invented universal five-recipient/one-retry/one-return defaults here. Deliveries deduplicate by origin, recipient, route generation and consumed basis. A revised route or input is an explicit generation retaining prior acknowledgements and effects.

Feedback edges may form cycles and support unattended review/revision. Following a permitted edge consumes the appropriate budget and records its cause; revisiting the same delivered origin/generation does not mint another request. A new revision can legitimately re-enter a reviewer under its declared iteration contract. A recipient cannot enlarge the permitted network or authority silently. One aggregate origin panel presents useful returns, current iteration and remaining limits; an unavailable recipient can recover automatically if the policy permits it. Stop/escalation is local to the exhausted or unmet contract, not global programme reset.

A draft remains pinned to its starting basis. If the original paragraph moved, the owner must readdress or request comparison. The frontend does not reuse a positional block ID or borrow fresh source tokens for old text. An unrelated section/simulation stays current unless it consumed the changed meaning. The exact relevance selector and affected-cone semantics are a backend construction, not a UI/library inference.

### Worked comment cycle: a material edge generation is not a transport attempt

One owner-banked origin is `C0/c1`, anchored to paragraph P4 and its source basis. W, R and S are existing selected writer/reviewer/simulation recipients; unrelated literature L is outside the route. A semantic role is a purpose/assignment label. The current dispatch execution role (`worker`/`judge`), actual session mode, provider binding, review independence/input contract and granted effect scope are separate owner facts. Naming a role Reader never grants review acceptance; naming one Writer never grants source application. Document-only context is a separate sealed admission contract, not a label or the ordinary review mode.

The proposed routing adapter extends the existing Work handoff/delivery/review/turn owners; it does not create a message ledger or a Work per ACK. Its edge identity is translated into the existing delivery owner’s handoff, binding revision, obligation, Work material scope and content-pin inputs; it does not replace that owner’s event/request identity or drop its admission rechecks. It gives each selected relation a stable edge identity and a material generation issued when that edge’s consumed inputs/relevance/recipient contract actually change. A route-panel revision can change display provenance without changing every edge generation.

The feedback admission point is the existing Work delivery submission/reservation owner extended for this route, before transport/turn admission. It validates the edge material basis, recipient binding/grant and remaining run/loop policy, and claims budget once for that event under the owning run’s admission boundary. Recovery reuses both event/request and claim; it cannot charge a fresh iteration or reset allowance. How a terminal unlaunched attempt releases a claim is an explicit owner policy, not a renderer decision. This requires an extension of existing run/Work phase accounting, not a second budget/message ledger or scheduler.

The current delivery contract admits review recipients only. Reusing its identity/reservation/recovery does not pretend it already launches arbitrary writers or simulations: W/S need declared adapter admission through the actual turn or research-run owner with their scoped grants. A review binding cannot grant source or simulation effects. Unsupported recipient contracts remain local gaps until that P4 extension is admitted.

Material generation, causal iteration and transport attempt are distinct. The budget belongs to the admitted run/loop, shared across its allowed re-entry; a new v6 generation cannot renew its own allowance. Relevance or authority changes on S may require a new edge generation/revalidation, but an unrelated route-plan edit may not. This is a specified missing routing contract, not a claim that the current single-recipient review-delivery owner already implements every row.

## 6. Worked routes

### A. Build and explain a workflow

A new user chooses an “Explain a result” example definition, reads its purpose and sees Idea → Sources → Plan → Draft → Review → PDF. This is a synthetic design template, not a new scientific run. They add an alternative idea branch, connect its return to Plan, and nest an evidence-check role beside the reader role inside Review. Drag/drop and outline commands produce the same proposed definition mutation. A role card exposes purpose, inputs/outputs, model, instruction origin, budget, reviewer relationship and granted effects.

Before saving, the owner explains the new relationship and any unsupported composition. The person selects automatic advance with independent review before source application, explains that review can run unattended while source effects retain their separate gate, and saves a definition version. Start is a separate action with a scoped run/grant preview. Unavailable generic definition operations are explicit construction requirements, not fake functional buttons.

### B. Comment while drafting

The person selects a paragraph while its draft role is working and opens “Send feedback”. Their text, exact source basis and chosen purpose are preserved. The configured automatic routing policy sends the saved comment to Section work, reader plan and one supporting simulation, with unrelated literature work omitted. The person opens the routing panel to inspect or change that permitted scope; no second Send is mandatory. The panel shows two acknowledgements and one unavailable recipient, applies its configured local retry policy, and retains useful returns while that recipient recovers. A changed source holds the original draft for comparison. The person can stop before the next source write without cancelling the unrelated branch. One aggregate return shows what changed, what still needs a decision and the action to continue.

### C. Override settings during a run

The person opens Draft → Writer → Model/Instructions. The inspector shows the global declaration, the project instruction segment and the role’s effective value, with separate permission ceiling. They save a role override for the next definition version. The active role stays on its admitted v4 basis. To use v5, they choose the owner-supported boundary: wait, stop-before-next or replan. A stale save retains their proposed value and compares the changed setting. Looking through the agent door must reveal the same effective basis and denied permission expansion, not a separate preference calculation.

### D. Change an operation contract

An operation’s implementation changes and a specific consumer expectation becomes invalid. The owner follows qualified consumed-meaning links to the affected human control, agent tool declaration and explanatory claim/review. These are shown as needing reconsideration with exact version/basis and repair scope; an unchanged neighbour stays current. An import graph can locate candidate code consumers but does not prove a documentation claim stale or current. Scoped implementation, control and claim repair yields inspectable new versions and receipts. An unaddressed local obligation remains visible without recursively demanding that the whole programme prove itself again.

The current engineering-support and project-guidance owners already preserve explicit Work/meaning/validation bases. The complete cross-object propagation is still incomplete. Stale published entry documentation is an actual calibration for this route, not a defect silently repaired by this document.

## 7. Conversation, material, explanation and access

Conversation is attached to a selected owner/object and purpose, with the exact existing session context and admitted target scopes. ## 9. Frontend boundaries and migration

A renderer consumes a selected object-region model, owner action descriptors and non-authoritative presentation preferences. It emits intents to an interaction controller. It owns rendered nodes, focus behaviour and temporary gestures; the controller owns the visit and command attempt; the existing draft owner owns unsaved text and its original basis. Backend owners remain authoritative for lifecycle/configuration/currentness/effects.

Services are explicit dependencies: qualified owner IO; operation/receipt/refusal presentation; region navigation/return; draft custody; scoped observation; and contextual explanation. They do not import the root shell or read global DOM to discover context. Domain adapters add manuscript, Work, research/material and role meaning. React is a presentation consumer of those services, not a new authoritative store.

A mounted region has a selection/generation, cancellation signal and one disposal path. Late reads cannot paint a replaced visit. Observers stop when hidden/destroyed, advance their cursor only after delivery, and preserve the owner’s expiry/recovery meaning. A cached read can support display but cannot supply a fresh write grant. DOM replacement never clears retained drafts implicitly. The existing iframe bridge remains origin-and-exact-frame fenced during transition; retiring it requires demonstrated replacement of every actual producer/consumer route, not a filename rename.

The canvas has explicit gesture meaning. Moving a card changes layout preference only. Connecting ports proposes one declared relation. Dropping into a container previews a typed Nest operation; React Flow `parentId` is updated only as a presentation of the admitted result. Deleting a node previews affected relations and running uses. Geometry changes during a drag stay local; the operation is admitted at a defined commit boundary, not once per pointer event. If the definition moved concurrently, retain the proposed gesture and offer a comparison. Visual undo can reverse local layout; undoing a committed semantic change requires the owner’s real revert/recovery action.

React’s component tree and React Flow’s internal gesture/layout state remain presentation state. Stable controller snapshots expose owner results, while subscriptions reread only the affected selected region. Commands are event-driven admitted attempts, never effects launched merely because a component mounted or rendered. A service owns each stream/timer/subscription and can be disposed or handed to another renderer. The retained draft and original basis survive such a handoff. No global frontend reducer infers canonical lifecycle/currentness from arbitrary messages.

A registry of presentation adapters selects graph, outline/list, document or a permitted custom renderer for a facet. It contains no permissions or new lifecycle states. Graph and list share the same selected region and commands. A replacement must demonstrate both reading a selected region and performing/recovering one admitted action without using hidden shell state. This is the concrete portability check for the interface boundary.
